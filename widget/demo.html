Replicating Postgres to Apache Iceberg

Stream changes from PostgreSQL into Iceberg tables with OLake: an initial full load, followed by continuous change data capture (CDC).

Tip: have a question that this page doesn't answer? Click the chat button in the bottom-right corner to ask the OLake docs assistant.

Postgres CDC

OLake reads changes from Postgres using logical replication. Every insert, update and delete written to the write-ahead log (WAL) is decoded by a replication slot and turned into rows in your Iceberg tables, so downstream engines always see a fresh copy of the source.

Prerequisites

  • PostgreSQL 10 or newer with wal_level = logical.
  • A user with the REPLICATION attribute and SELECT on the tables you sync.
  • A publication covering those tables and a replication slot that OLake can consume.
ALTER SYSTEM SET wal_level = logical;
-- restart Postgres, then:
CREATE PUBLICATION olake_pub FOR ALL TABLES;
SELECT pg_create_logical_replication_slot('olake_slot', 'pgoutput');

Once the slot exists, point the OLake source configuration at it. The first run performs a parallel, chunked full load; subsequent runs resume from the last confirmed LSN, so a sync can be stopped and restarted without losing changes.

Iceberg catalogs

OLake writes open Apache Iceberg tables and registers them in the catalog of your choice, so query engines such as Trino, Spark, Snowflake or DuckDB can read them immediately.

CatalogTypical use
AWS GlueAWS-native lakehouses on S3
REST catalogPolaris, Nessie, Lakekeeper, Unity and other REST-compatible services
Hive MetastoreExisting Hadoop or on-prem deployments
JDBCLightweight setups backed by Postgres or MySQL

The catalog is configured in the destination settings together with the object-store location and credentials.

OLake Fusion compaction

Streaming CDC produces many small data files and delete files. OLake Fusion keeps tables healthy by compacting them in the background: it rewrites small files into larger ones, applies accumulated equality and position deletes, and expires obsolete snapshots, so query performance and storage costs stay predictable as the table grows.

Compaction runs independently of ingestion, so replication latency is unaffected while maintenance happens.
